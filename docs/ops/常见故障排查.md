# 常见故障排查

统一格式：**① 用户会看到什么 → ② 最常见原因 → ③ 先检查哪里 → ④ 具体操作 → ⑤ 如何确认已解决 → ⑥ 不要贸然尝试的事**。

排查总原则：**先确定问题在哪一层**（网站 / 认证 / 数据库 / 托管），再动手。每一层都有独立的判据，见 [网站更新与部署.md 第 6 节](./网站更新与部署.md)。

---

## 故障 1：新成员注册失败

**① 现象**：填写邮箱密码点「提交申请」后，右上角弹红色提示，或转圈没反应。

**② 最常见原因**（按概率排序）
1. 密码太短（当前策略最少 6 位）。
2. 该邮箱已注册过（提示「邮箱已存在」类信息）。
3. 浏览器里存的连接配置被改错（本机 localStorage 覆盖了仓库默认值）。
4. Supabase 项目被暂停。

**③ 先检查哪里**
- 看提示原文（把它当线索，不要凭猜）。
- 看右上角运行环境指示器是不是「Supabase 云端」（显示「本地沙箱演示」说明在沙箱模式，注册只写本机）。
- F12 → Network，看那条 `signup` 请求的状态码。

**④ 具体操作**
1. 让成员换一个邮箱试一次，排除「已注册」。
2. 打开 https://supabase.com/dashboard 确认项目状态是 `ACTIVE_HEALTHY`（不是 `PAUSED`）。
3. 检查本机配置：点网站右上角指示器 → 把 URL 与 Key 两栏**清空** → 保存 → 页面会自动刷新回到仓库默认配置。
4. 若 `signup` 返回 422/400，读 `message` 字段，通常是密码或邮箱格式。
5. 用 PowerShell 直接测注册接口（把 `<PUB_KEY>` 换成 Publishable key）：
```powershell
curl.exe -X POST "https://qbeqynsibnsvvgwyhfyy.supabase.co/auth/v1/signup" `
  -H "apikey: <PUB_KEY>" -H "Content-Type: application/json" `
  -d '{\"email\":\"probe@yiya-lab.test\",\"password\":\"Test#123456\"}'
```
返回一大段含 `access_token` 的 JSON = 后端正常，问题在这个成员的输入或浏览器。

**⑤ 确认解决**：该成员能收到「等待审核」提示页，且你在管理员专区或 `users_profile` 表里能看到他的邮箱。

**⑥ 不要做**：不要为了排查去改 Supabase 的注册开关或 RLS；不要反复尝试导致触发限流（`rate_limit_anonymous_users = 30`）。

## 故障 2：注册成功但无法登录

**① 现象**：注册明明成功了，回头登录却报「邮箱或密码错误」，或登录后一直停在等待审核页。

**② 最常见原因**
1. 密码记错（注册时没注意大小写/中文输入法下的全角字符）。
2. 注册时用的是 A 邮箱，登录输入了 B 邮箱。
3. 登录成功但状态是 `pending`，被路由到等待页——**这不是故障，是设计**。
4. 邮箱确认被打开过（当前 `mailer_autoconfirm = true`，正常不该出现）。

**③ 先检查哪里**：Supabase → **Authentication → Users** 搜这个邮箱。

**④ 具体操作**
- Users 里**查不到**这个邮箱 → 他没注册成功，回到故障 1。
- Users 里**查得到** → 在 SQL Editor 跑：
```sql
SELECT p.email, p.status, p.role,
       (a.email_confirmed_at IS NOT NULL) AS 邮箱已确认,
       (a.banned_until IS NOT NULL) AS 已封禁
FROM public.users_profile p
LEFT JOIN auth.users a ON a.id = p.id
WHERE p.email = '该成员邮箱';
```
  - 查不到行 → 档案缺失（触发器没生效，需维护者查），临时手工补一行。
  - `status = pending` → 走审核流程（成员管理文档 3.1）。
  - `已封禁 = true` → Users 里对他解除封禁。
  - 状态正常但仍报密码错 → 只能重置密码，见故障 6。

**⑤ 确认解决**：该成员登录后能看到「等待审核」或正常页面，且与你查到的 `status` 一致。

**⑥ 不要做**：不要直接 `DELETE FROM auth.users` 让他重新注册——有借还记录的人删不掉（外键限制），而且删了会切断历史关联。

## 故障 3：用户登录成功，却看不到耗材数据

**① 现象**：能进系统，但列表空白、统计显示 0，或提示「暂无数据」；数据库里明明有东西。

**② 最常见原因**
1. **缺陷 R1**（前端字段名不匹配）——**目前这是最可能原因**，且对**所有**云端用户都成立。
2. 账号状态不是 `approved`（RLS 返回 0 行）。
3. 所有物资都被「停用」，而列表默认隐藏已停用项。
4. 他看的是沙箱模式，里面没有真实数据。

**③ 先检查哪里**：右上角指示器（云端/沙箱）→ SQL 查状态 → 数据库里到底有没有数据。

**④ 具体操作**
1. 确认指示器显示 **Supabase 云端**。
2. 跑这条确认他的权限：
```sql
SELECT email, status, role FROM public.users_profile WHERE email = '他的邮箱';
```
3. 确认数据库确实有数据：
```sql
SELECT count(*) AS 总数, count(*) FILTER (WHERE is_active) AS 启用中
FROM public.materials_3d;
```
   当前应为 5 / 5。
4. 如果 2 是 `approved`、3 有数据、界面仍空白 → **就是 R1**，不是你的操作问题，也不是权限问题。让维护者按总览文档的修复方案处理。
5. 判别技巧：让他打开 `?mode=sandbox`，沙箱模式下列表有数据 → 说明代码没崩，是真实数据读取的映射问题。

**⑤ 确认解决**：R1 修好后，该成员刷新能看到 5 条线材、姓名出现在概览统计里。

**⑥ 不要做**：不要在 Table Editor 里为了「让他看到」而乱改数据；不要关掉表的 RLS（那会把数据对全世界敞开）。

## 故障 4：待审核成员意外获得访问权限

**① 现象**：你确认某人还是 `pending`，但他说他能看到物资数据。

**② 最常见原因**
1. 他其实已经被批准了（你看的列表没刷新，或看错了行）。
2. 他手里有另一个 `approved` 的旧账号（同一人两个邮箱）。
3. 他在**沙箱模式**下看到了内置示例数据，误以为是真实数据。
4. 极少数：RLS 策略被人为改动或关闭。

**③ 先检查哪里**：先分清他看到的是「真实台账」还是「示例数据」。示例数据里的名字是「陈老师 / 张同学 / 拓竹 PLA Basic 哑光白」这类。

**④ 具体操作**
1. 让他截图整页，重点看**右上角指示器**和浏览器地址栏有没有 `mode=sandbox`。
2. 跑 SQL 核对状态：
```sql
SELECT email, status, role, to_char(created_at,'YYYY-MM-DD') AS 注册
FROM public.users_profile ORDER BY status, created_at;
```
3. 核对 RLS 是否全部在位（预期 8 张表 `relrowsecurity` 全为 true）：
```sql
SELECT c.relname, c.relrowsecurity
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r' ORDER BY 1;
```
4. 核对策略条数（预期总计 24 条，分布见后台指南第 5 节）：
```sql
SELECT tablename, count(*) FROM pg_policies
WHERE schemaname = 'public' GROUP BY 1 ORDER BY 1;
```
5. 若第 3、4 步出现异常（某表 RLS = false，或 `inventory_logs` 多出 INSERT 策略）→ **立即视为安全事件**：通知维护者，暂时把该批成员状态改为 `disabled`，查 Supabase **Audit Logs** 与 **Logs** 找是谁改的。

**⑤ 确认解决**：用他的账号（或让他配合）验证读物资接口返回空；策略数量回到预期值。

**⑥ 不要做**：不要「先关掉 RLS 看看是不是它的问题」——这一步在生产库上等于把数据公开。要看效果请在第二个免费项目上做。

## 故障 5：管理员无法审核成员

**① 现象**：点「准入为普通成员」弹红字，或管理员专区页面显示「访问受限：需要管理员权限」。

**② 最常见原因**
1. 当前登录的账号不是 `admin`（或状态不是 `approved`）。
2. **唯一管理员把自己禁用了**——系统有 `ERR_LAST_ADMIN` 保护，正常不会发生，但如果是在 Table Editor 手工改的，保护会被绕过。
3. 待审核列表为空（申请人档案行没建出来）。
4. 凭证过期（R2，1 小时）。

**③ 先检查哪里**：SQL 看全系统有几个能用的管理员：
```sql
SELECT email, role, status FROM public.users_profile
WHERE role = 'admin' ORDER BY status;
```

**④ 具体操作**
- 情况 A：一个 `role=admin` 且 `status=approved` 都没有 → 用 SQL 恢复一个：
```sql
UPDATE public.users_profile
SET role = 'admin', status = 'approved', reviewed_at = now(), updated_at = now()
WHERE email = '你的管理员邮箱';
```
  然后**重新登录**（浏览器缓存的旧身份需要刷新）。
- 情况 B：管理员正常，但点按钮报错 → 读错误消息：
  - `ERR_NOT_APPROVED` → 你自己的状态有问题；
  - `ERR_FORBIDDEN` → 角色不是 admin；
  - `ERR_LAST_ADMIN` → 你在动唯一的自己，先设第二个管理员；
  - `permission denied for function` → 你未登录（凭证过期），重新登录。
- 情况 C：待审核列表空白但认证中心有新用户 → 建档触发器可能失效：
```sql
SELECT count(*) AS 缺档案的账号数 FROM auth.users u
LEFT JOIN public.users_profile p ON p.id = u.id WHERE p.id IS NULL;
```
  不为 0 就跑这条补档（幂等，可重复执行）：
```sql
INSERT INTO public.users_profile (id, email, full_name, role, status)
SELECT u.id, coalesce(u.email, u.id::text || '@no-email.yiya-lab.local'),
       coalesce(nullif(trim(u.raw_user_meta_data ->> 'full_name'), ''),
                split_part(coalesce(u.email,''), '@', 1), '未命名成员'),
       'member', 'pending'
FROM auth.users u
WHERE NOT EXISTS (SELECT 1 FROM public.users_profile p WHERE p.id = u.id)
ON CONFLICT (id) DO NOTHING;
```

**⑤ 确认解决**：待审核列表出现该成员，点批准后他从列表消失并能在网站看到数据。

**⑥ 不要做**：不要为了「先让他能用」去关 RLS；不要给成员发 secret key；不要同时改多个人的角色（一次一人，方便回退）。

## 故障 6：用户忘记密码

**① 现象**：成员说密码忘了，登录一直失败。

**② 最常见原因**：就是忘记密码；其次是中文输入法导致注册时密码含全角字符。

**③ 先检查哪里**：让他**复制粘贴**密码输入（排除输入法问题），并确认邮箱正确。

**④ 具体操作（当前可行路径）**
1. **首选**：Supabase → **Authentication → Users** → 找到他 → **⋯** → **Send reset password**。
   - ⚠️ 前提是 Site URL 已改成 `https://wrm-fw.github.io/yiya-lab-inventory/`（当前**仍是 `http://localhost:3000`，未改则此路不通**）。
   - 内置发信限速**每小时 2 封**，别连点。让他查垃圾箱。
2. **配置好发信之前**：让他重新注册一个新邮箱账号（实验室内部邮箱多），旧账号在 Users 里禁用。**注意**：他名下的未归还借还单需要手工处理，因为旧账号删不掉。
3. 长期方案：配置自定义 SMTP（**Authentication → Emails → SMTP**），或让维护者在前端加「忘记密码」入口（当前没有）。

**⑤ 确认解决**：他用新密码登录成功，且 `users_profile` 里他的状态仍是 `approved`。

**⑥ 不要做**：不要直接删账号重建（历史流水的 `operator_id` 会断链）；不要把自己的管理员账号借给他用。

## 故障 7：网站更新后没有变化

**① 现象**：改了文字推送了，线上还是旧的。

**② 最常见原因**：只 commit 没 push > 浏览器缓存 > 改了没保存 > 构建排队。

**③ 先检查哪里**：
```powershell
cd D:\Users\28322\Desktop\Qoder_Project\RestWeb_Develop\yiya_lab_inventory
git status
git log --oneline -3
```

**④ 具体操作**：按 [网站更新与部署.md 第 4 节](./网站更新与部署.md) 逐步走：`ahead of origin` → push；无痕窗口验证；Insights → Pages 看构建状态。

**⑤ 确认解决**：无痕窗口打开线上地址能看到新内容；或 `curl` 该文件确认内容已变：
```powershell
curl.exe -s "https://wrm-fw.github.io/yiya-lab-inventory/index.html?v=1" | Select-String "你改的关键词"
```

**⑥ 不要做**：不要反复 push 同一改动「碰运气」；不要 `git reset --hard` 把还没备份的本地改动抹掉。

## 故障 8：网站能打开，但数据库请求全部失败

**① 现象**：界面正常显示，但所有页面转圈后报错，成员集体反馈「用不了」。

**② 最常见原因**：Supabase 项目被暂停（1 周无请求）> 网络到 `*.supabase.co` 不通 > 连接配置被改坏 > 免费额度耗尽。

**③ 先检查哪里**：Supabase 首页项目状态；F12 Network 里请求的状态码。

**④ 具体操作**
1. 项目显示 `PAUSED` → 点 **Restore**，等 1 分钟。数据无损。
2. 项目正常但请求 `ERR_NETWORK` / 超时 → 校园网/代理屏蔽了 `supabase.co`。让成员换手机热点验证，确认是网络侧问题。
3. 请求 401 且所有人都这样 → 凭证过期叠加缓存（R2），让大家重新登录。
4. 只有某台机器不行 → 该机 localStorage 里存了错误的 URL/Key：点右上角指示器清空两栏保存。
5. 检查额度：**Project Settings → Usage**，看数据库体积是否逼近 500 MB（超了会变**只读**，表现就是「看得到但存不进」）。

**⑤ 确认解决**：成员能正常录入一条流水并在审计页看到它。

**⑥ 不要做**：不要为了恢复而删数据「腾空间」；不要重建项目（等于丢数据，除非你有完整备份）。

## 故障 9：数据被误删或误改

**① 现象**：某个耗材不见了、库存数字明显不对、某成员记录消失。

**② 先做一件事：停止继续操作。** 越晚恢复越难。

**③ 判断是「真删」还是「停用」**
```sql
SELECT name, is_active, remaining_weight_g FROM public.materials_3d ORDER BY name;
```
`is_active = false` 是停用，网站默认隐藏而已 → 在列表里打开「显示已停用」并点启用即可，**不需要恢复数据**。

**④ 查谁干的**
```sql
SELECT to_char(created_at,'YYYY-MM-DD HH24:MI') AS 时间, operator_name,
       target_name, operation_type, change_amount, previous_balance, new_balance, notes
FROM public.inventory_logs
WHERE created_at > now() - interval '2 days'
ORDER BY created_at DESC;
```
注意：网站内的正常操作都会留痕；**在 Table Editor 或 SQL 里手工改的不会留痕**——这也是为什么文档反复要求手工修改前先备份。

**⑤ 恢复**
- 只是数字错 → 用「反向操作」修正（管理员在网站上做一次入库/报损并写清备注），保住审计链。见 [备份恢复与安全.md 5.1](./备份恢复与安全.md)。
- 整行被删 → 从备份 CSV 手工 `INSERT ... ON CONFLICT DO NOTHING`。
- 大面积丢失 → 走灾难恢复（5.3），并立刻通知所有人停用系统。

**⑥ 不要做**：不要 `TRUNCATE` 某张表「重新导入」；不要在没有备份时执行任何 `DELETE`；不要试图编辑 `inventory_logs` 来「抹掉痕迹」——这张表被 RLS 设计成不可直接改写，硬改会让台账失去可信度。

## 故障 10：Supabase 达到免费额度或服务不可用

**① 现象**：写入报「数据库只读」；或收到 Supabase 邮件说超出限额；或 Dashboard 提示项目将被暂停。

**② 官方 Free 档限额（已核实）**：数据库 **500 MB**、**50,000 月活用户**、出站流量 **5 GB/月**、日志保留 **1 天**、**无自动备份**、**1 周无活动自动暂停**、单账号 **2 个活跃项目**。当前你的用量：数据库 11 MB、成员 0 人——离限额极远。

**③ 先检查哪里**：**Project Settings → Usage**（图表会显示各项用量）。

**④ 具体操作**
1. 数据库体积接近上限 → 先做完整备份，再考虑清理。本项目最可能膨胀的是 `inventory_logs`，但它是审计流水，**不该删**。真要腾空间，正确做法是导出 CSV 归档后由维护者评估清理，而不是直接删。
2. 流量超限 → 一般是被人拿网址刷数据。检查 **Logs** 里的异常来源；考虑在 **Authentication → Attack Protection** 加防护。
3. 项目被暂停 → Restore；随后建立「每两周访问一次」的排班（寒暑假尤其重要）。
4. 确实不够用 → 说明实验室规模超出免费方案设计，此时讨论升级或迁移到校内服务器（数据可移植，见部署指南第 10 节），**不要**在慌乱中删数据。

**⑤ 确认解决**：Usage 各指标回落到安全区，成员读写正常。

**⑥ 不要做**：不要为了省空间关掉数据写入功能；不要误点 **Subscription** 里的升级（会产生费用）；不要新建第二个项目当备用又忘了额度只有 2 个。

## 故障 11：用了一小时后点什么都报错（已知缺陷 R2）

**① 现象**：上午好好的，下午点按钮弹红字或数据加载失败，但右上角还显示着他的名字。

**② 原因**：登录凭证有效期 1 小时（`jwt_exp = 3600`），前端没有自动续期。

**③ 操作**：让他按 **Ctrl + F5** 刷新，回到登录页重新登录即可恢复。

**④ 根治**：需要改前端（401 时自动清缓存并跳登录页）。已登记为 R2，等你确认后再改。

## 故障 12：页面出现 undefined、NaN、统计为 0（已知缺陷 R1）

见故障 3。这是当前**云端模式的普遍现象**，不是成员操作造成的，也不要试图通过改数据库来「让它显示出来」。

## 求助时请提供这些信息

给维护者（或 AI 助手）描述问题时，附上这 6 项能省掉一半来回：

1. 什么时候开始、之前做过什么操作（改过代码？跑过 SQL？换过网络？）。
2. 影响的范围：一个人 / 所有人 / 某个功能。
3. 报错原文截图（含 F12 → Console 与 Network 的红色条目）。
4. 右上角运行环境指示器显示什么（云端 / 沙箱）。
5. 这条 SQL 的结果：
```sql
SELECT (SELECT count(*) FROM auth.users) AS 账号数,
       (SELECT count(*) FROM public.users_profile WHERE status='approved') AS 已通过,
       (SELECT count(*) FROM public.materials_3d) AS 线材数,
       (SELECT count(*) FROM public.inventory_logs) AS 流水数;
```
6. Supabase 首页显示的项目状态（`ACTIVE_HEALTHY` / `PAUSED` / 其他）。

**什么时候该停手**：出现「看不懂的数据在减少」「RLS 状态和文档不一致」「需要执行别人给的 SQL 才能修好」这三种情况，立即停止操作、保留现场、通知维护者。
