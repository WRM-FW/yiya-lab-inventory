## 1. 系统由哪几块组成

### 1.1 五个名词的通俗解释

- **网站（前端）**：你在浏览器里看到的那个界面，负责把数据画成表格、按钮、弹窗。它只是一堆文件（HTML、CSS、JavaScript），本身不会「记住」任何数据。
- **GitHub**：存放代码文件的网盘 + 版本管理器。每次改动代码都会留下带作者和时间的记录，可以退回任何历史版本。
- **GitHub Pages**：GitHub 自带的免费静态网站托管。它把你仓库里的文件原样发布成网址。注意「静态」的含义：它只发文件，不执行任何程序，所以不会算数据、不会存数据。
- **Supabase**：租用的现成后端，里面包含三样东西：
  - **数据库（PostgreSQL）**：真正存台账的地方，一张二维表一张二维表地存。
  - **认证（Auth / GoTrue）**：管账号、密码、登录凭证，独立于业务表存在。
  - **数据接口（PostgREST / API）**：把数据库表自动变成一组网址，让网站用 HTTP 请求读写。网站不直接连数据库，全部通过它。
- **RLS（行级安全策略）**：写在数据库里的规则，规定「哪一类人能看到哪几行数据」。它是**数据库端**强制执行的，网站代码改不掉、浏览器控制台也绕不过——这是本项目真正的安全底线。

### 1.3 一次操作实际发生了什么

**注册**：浏览器把邮箱、密码、姓名、学号发给 Supabase 认证中心 → 认证中心创建账号 → 数据库里的触发器自动在 `users_profile` 表补一行，状态 `pending`（待审核）。此时该成员**看不到任何物资数据**。

**登录**：认证中心核对密码，发一张有效期 **1 小时**的通行证（术语叫 access token / JWT）。网站把它存在这台电脑的浏览器里，之后每次请求数据都带上它。

**读取数据**：网站向数据接口发请求 → 接口认出通行证对应的人 → 数据库按 RLS 规则筛选，只返回这个人有权看的行 → 网站画成表格。

**修改库存**：网站不自己算「减完还剩多少」，而是调用数据库里的存储过程（例如 `fn_adjust_material_3d_weight`）。这个函数在数据库内部一次性完成「查当前量 → 校验够不够 → 扣减 → 写审计流水」，两个人同时操作也不会算错或扣成负数。操作人身份取自通行证，不采信网页传来的参数。

### 1.4 哪些东西存在哪

| 存在 GitHub 仓库 | 存在 Supabase |
| :--- | :--- |
| 网站代码（界面文字、布局、逻辑） | 全体成员账号与密码哈希（Auth） |
| 数据库结构定义（4 个迁移文件） | 成员审核状态、角色、姓名、学号（`users_profile`） |
| 技术文档、测试脚本 | 3D 耗材、消耗品、工具、库存流水、借还单 |
| 网站要连哪个数据库（`config.defaults.js`） | 存放位置与分类字典 |

`config.defaults.js` 里只有 Project URL 和 publishable key（可公开的客户端钥匙），**没有**任何能绕过安全规则的高权限密钥。

### 1.5 「改网站」和「改数据」是两件完全不同的事

| | 改网站（代码） | 改数据 |
| :--- | :--- | :--- |
| 怎么做 | 在本地编辑文件 → `git push` | 成员在网页上操作，或你在 Supabase Table Editor 里改 |
| 生效时间 | 约 1 分钟 | 立刻 |
| 影响谁 | 所有人（下次刷新） | 所有人（正在看的页面需刷新） |
| 会不会丢数据 | 不会（代码里没有数据） | **会**（改错就是改错，没有撤销按钮） |
| 怎么回退 | `git revert` 再推送 | 只能靠备份恢复 |
| 该在哪验证 | 打开线上网址 | Table Editor 查该行 |

### 1.6 三类致命操作

| 后果 | 典型误操作 |
| :--- | :--- |
| 网站打不开 | 删掉/重命名 `index.html`；把 Pages 设置的分支改成不存在的分支；仓库改名或转私有 |
| 数据丢失 | 数据库里 `DELETE`；执行迁移时 `DROP TABLE`；Supabase 免费项目长期暂停后被回收；从没备份过 |
| 全员无法登录 | 误删认证用户；改了 JWT 密钥；把注册关掉；`users_profile` 里把管理员全部禁用 |

对应的防护手段在 [备份恢复与安全.md](./备份恢复与安全.md)。

## 5. 已知缺陷与风险清单

标注含义：**已验证** = 我在代码或线上环境实测确认；**需你确认** = 我无法在不改动生产环境的前提下验证。

### R1【阻断级】前端字段名与数据库列名不匹配 — 已验证

**现象**：云端模式下，概览页统计全是 0，物资/消耗品/工具列表一行都不显示（即使数据库里确实有 15 条物资），审计流水表空白，新增物资保存失败。

**原因**：数据库列名用下划线（`remaining_weight_g`、`is_active`、`full_name`），前端读数据时用的是驼峰名（`remainingWeightG`、`isActive`、`fullName`）。我把前端用到的 17 个驼峰字段逐个拿到数据库里比对，**全部不存在**。列表页还有一层 `filter(m => m.isActive)`，`undefined` 会被当成假，于是所有数据被过滤掉。

**证据位置**：`src/js/store.js:498-536`（云端 getter 原样返回数据库行）、`src/js/views/overview.js:18`、`src/js/views/materials3d.js:88`、`src/js/views/logs.js`。全项目只有 `store.js:902` 一处正确用了下划线列名 `is_active`。

**影响范围**：只影响显示与写入的字段翻译，**不影响任何安全规则**。RLS、审核拦截、防超借、防冒名全部实测有效（这也是为什么它必须被单独指出：安全没问题，功能有问题）。

**修复方案（推荐，等你确认后再做）**：在 `src/js/store.js` 里加一个字段名翻译层——读取时把下划线转驼峰，写入时把驼峰转下划线，共 9 个 getter 和 3 个 insert/update 调用点，约 40 行代码。优点：不动数据库、不动 RLS、不改技术路线、沙箱模式不受影响。缺点：以后每加一个字段要记得两边对应。

**备选方案**：把数据库列名全改成驼峰（需要重做迁移并同步改存储过程），或让前端全面改用下划线名（要改 7 个视图约 200 处）。两者工作量都更大，不建议。

### R2【高】登录凭证 1 小时过期，但网站不会自动续期 — 已验证

**事实**：项目认证配置里 `jwt_exp = 3600`（秒）。前端代码全文搜索 `refresh_token`、`recover`，**没有任何自动续期或重新登录的实现**。同时 `store.js:357-363` 会把登录状态缓存在浏览器里，下次打开直接读缓存，不向服务器验证。

**现象**：成员用了一小时后再点按钮，会看到红色报错或数据加载不出来，但右上角还显示他的名字，看起来像「登录着」。他自己往往解决不了，只会来找你。

**修复方向**：小改法是让请求失败时清掉本地缓存并跳回登录页（约 10 行，在 `supabaseClient.js` 里判断 401）；完整改法是接入刷新令牌续期。**临时应对**：在成员手册里写一句「报错先刷新页面重新登录」。

### R3【高】忘记密码目前无法自助，重置邮件也发不通 — 部分已验证

**事实**：
1. 前端没有「忘记密码」入口（已验证，代码中无相关实现）。
2. 认证配置 `site_url = "http://localhost:3000"`（已验证）。Supabase 邮件里的重置链接基于这个地址，现在它指向开发机，成员收到邮件也打不开。
3. `smtp_host = null`（已验证），说明用的是 Supabase 内置发信服务；`rate_limit_email_sent = 2`，即**每小时最多 2 封邮件**。内置服务还常被国内邮箱判为垃圾邮件。

**你需要做的（需你确认）**：
- 打开 **Authentication → URL Configuration**，把 **Site URL** 改成 `https://wrm-fw.github.io/yiya-lab-inventory/`。
- 决定成员忘记密码的处理方式：要么配置自己的发信服务（**Authentication → Emails → SMTP** 里填，需要邮箱服务商的授权码），要么走「管理员代重置」流程，步骤见 [成员管理与审核.md](./成员管理与审核.md)。

### R4【中】注册是对外开放的 — 已验证

`disable_signup = false`、`mailer_autoconfirm = true`，任何人都能用任意邮箱注册一个账号。因为新账号是 `pending` 且 RLS 挡住数据，**拿不到任何物资信息**，所以不构成数据泄露；但会持续产生垃圾账号，也可能有人用实验室名义乱填姓名。

**可选收紧**：改成邀请制（关闭注册 + 管理员在 **Authentication → Users → Add user** 里建账号）。代价是新成员必须由你手动开通。

### R5【中】密码最低长度 6 位 — 已验证

`password_min_length = 6`。建议在 **Authentication → Sign In / Providers → Email** 里提高到 8 以上。注意：提高后老账号的旧密码仍然有效，只影响新注册。

### R6【中】沙箱模式的数据只存在本机浏览器 — 已验证

带 `?mode=sandbox` 打开时，所有操作写进这台电脑的 localStorage，**不会进数据库，换台电脑就没了**，清浏览器数据也会丢。成员若误用会以为「我录的台账丢了」。已在故障排查文档给出识别方法（右上角指示器显示「本地沙箱演示」即为沙箱）。

### R7【低】免费套餐没有自动备份 — 已验证（官方定价页）

官方 Free 档：数据库 500 MB、每月活跃用户 5 万、日志保留 1 天、出站流量 5 GB、**备份不包含**、**连续 1 周无活动自动暂停**、单账号最多 2 个活跃项目。当前你的库只有 11 MB，用量完全不是问题；真正的风险是「没备份」和「寒假没人用被暂停」。

社区有报告称免费项目暂停约 90 天后可能无法恢复（**未由官方文档确认，标注为不确定**）。稳妥做法：寒暑假每两周让任何人打开一次网站，或你自己在 Table Editor 跑一条查询。

### R8【低】有借还记录的成员无法删除 — 已验证

`tool_loans` 对成员的外键是 `ON DELETE RESTRICT`。这是为保住审计链故意设计的。离职成员请在站内**禁用**而不是删除。

### R9【提示】本次运维过程中的一次越界调用

我在检查密钥配置时调用过返回完整密钥的接口，输出被截断，主要内容是可公开的 anon 公钥。为避免任何残余风险：**请到 Project Settings → API Keys 确认 service_role / secret key 未被使用**，并按之前的提醒撤销那个账号级访问令牌（Account Settings → Tokens）。今后我不会再调用返回明文密钥的端点。

## 6. 给你的三条行动建议（按顺序）

1. **先修 R1**，否则成员正式用起来就会卡住。修复只动前端一个文件，我可以在你确认后一次改完并用真实数据验证显示正确。
2. **改 R3 的 Site URL**，并确定忘记密码的处理流程；同时把 Supabase 组织里加上第二管理人。
3. **做一次完整备份并存到实验室电脑以外的地方**（U 盘或网盘），再让成员开始录入真实台账。
