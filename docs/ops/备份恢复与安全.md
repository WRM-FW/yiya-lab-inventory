# 备份恢复与安全

> 一句话原则：**任何会改数据的操作之前，先备份；备份要放到实验室电脑以外的地方。**
> 官方 Free 套餐**不含自动备份**（已核实），所以备份完全是你的责任。

## 2. 三档备份，按需选用

### 档位 A：学期末台账导出（最简单，5 分钟）

只导出流水，用于归档对账，**不能用来恢复系统**。

1. 管理员登录网站 → 顶部 **审计流水**。
2. 点右上角 **📥 导出 Excel / CSV 流水台账**。
3. 得到 CSV 文件，按学期命名，例如 `yiya_流水_2026-2027上.csv`。

**⚠️ 前提**：这条功能依赖前端读取 `inventory_logs` 表，而缺陷 R1 未修复前，云端模式下导出的内容会是空白列。**R1 修好之前请用档位 B。**

### 档位 B：全表 CSV 快照（当前推荐，不需要装任何东西）

1. Supabase 左侧 **SQL Editor** → **New query**。
2. 逐张表执行 `SELECT * FROM public.materials_3d;`（8 张表各一次），结果区右上角有 **Download CSV / 导出** 按钮，下载。
3. 8 张表 + 一个成员表，共 9 个文件（`users_profile`、`storage_locations`、`categories`、`materials_3d`、`general_consumables`、`reusable_tools`、`inventory_logs`、`tool_loans`）。
4. **认证账号（邮箱+密码）不在这些表里**，必须额外做档位 C，否则恢复出来的系统没人能登录。
5. 文件名带日期：`backup_20261012_materials_3d.csv`。

### 档位 C：完整结构 + 数据 + 账号（真正的灾难恢复备份）

这是唯一能「整机重建」的备份形态。三种做法，任选其一：

**做法 1：让维护者或 AI 助手用运维脚本导出**（不需要装东西）
仓库外的 `yiya_deploy_tools/` 已有连 Supabase 管理接口的脚本骨架，加一个导出脚本即可把 8 张表转成 `INSERT` 语句、把 `auth.users` 的邮箱与密码哈希导出。需要临时使用一次访问令牌，用完撤销。**这是目前对你最省事的路线**，需要你确认后再做。

**做法 2：本机安装 PostgreSQL 客户端后 pg_dump**
1. 装官方 PostgreSQL（含 `pg_dump.exe`），或用 Supabase CLI 自带的 docker 方案（需要 Docker）。
2. 在 **Project Settings → Database** 里拿到直连信息，并**开启 IPv4 直连**（默认可能只给 IPv6，国内网络会连不上——这是社区常见坑，**需你在界面确认**）。
3. PowerShell 执行（提示输入密码时填数据库密码）：

```powershell
pg_dump -h db.qbeqynsibnsvvgwyhfyy.supabase.co -U postgres -d postgres -F p `
  -f "D:\备份\yiya_lab_full_$(Get-Date -Format yyyyMMdd).sql"
```

4. 预期：命令安静结束，生成几 MB 的 `.sql` 文件。
5. 失败处理：`connection timed out` → 没开 IPv4 直连或网络不通；`password authentication failed` → 数据库密码不对，去 Settings → Database 重置。

**做法 3：迁移到新项目时**——用「结构 + CSV 数据」组合：新项目按顺序跑 4 个迁移文件建结构，再用 Table Editor 的 **Import data from CSV** 逐表导入档位 B 的文件，成员账号则请他们重新注册。这是最笨但最不容易出错的路线。

## 3. 备份的存放与验证

**存放规则（三条都要满足）**：

1. 至少两份副本。
2. 至少一份在**这台电脑之外**（实验室另一台机器、U 盘、学校网盘）。只存在本机等于没备份。
3. 文件名带日期，保留最近 6 次 + 每学期 1 次长期归档。

建议目录：`D:\备份\yiya_lab\20261012\`

**验证规则**：备份不验证就是薛定谔的备份。每次做完整备份后，抽查一条：

```sql
-- 用记事本打开备份文件，确认里面有真实数据行而不是只有建表语句
-- 或者：把备份里的某个数字和你现在网站上看到的对一下
SELECT count(*) FROM public.inventory_logs;
```

**恢复演练（每学期一次，最重要的一条建议）**：
用 Supabase 免费额度里的**第二个项目**（你有 2 个活跃项目额度），把备份恢复进去，登录网站看数据在不在。没做过演练的备份，真出事时基本恢复不出来。

## 4. 安全地修改数据库结构

场景：想给 3D 耗材加一列「采购单价」。

**铁律：不要改已经执行过的迁移文件。** 那 4 个文件是「历史」，改了以后没人知道线上库到底执行过什么版本。正确做法是**新增第 5 个文件**。

### 步骤

```powershell
# 1. 先备份（档位 B 或 C）
cd D:\Users\28322\Desktop\Qoder_Project\RestWeb_Develop\yiya_lab_inventory
git status        # 确认干净，没有未提交的杂项
```

2. 新建文件 `supabase/migrations/20261020000001_add_unit_price.sql`（文件名规则：`年月日时分秒_英文说明.sql`，时间戳必须比前一个晚）。内容示例：

```sql
-- 为 3D 耗材增加采购单价（元/克），可空，不影响既有数据
ALTER TABLE public.materials_3d
  ADD COLUMN IF NOT EXISTS unit_price_per_g NUMERIC(10,4) CHECK (unit_price_per_g >= 0);

COMMENT ON COLUMN public.materials_3d.unit_price_per_g IS '采购单价，元/克';
```

3. **先在本地或一个临时 Supabase 项目验证**（推荐：用你的第二个免费项目跑一遍 01→04 + seed + 新迁移）。
4. 到 Supabase **SQL Editor** 粘贴该文件内容 → Run。
5. 验证：左侧 **Table Editor** → `materials_3d`，应看到新列（值为空是正常的）。
6. 前端要显示这一列，还需改代码（并且要先解决 R1 的字段映射）。
7. 提交：

```powershell
git add supabase/migrations/20261020000001_add_unit_price.sql
git commit -m "feat(db): 3D 耗材增加采购单价列"
git push origin main
```

### 结构变更的风险分级

| 操作 | 风险 | 必须做的防护 |
| :--- | :--- | :--- |
| 加可空列 | 低 | 普通备份 |
| 加带 `NOT NULL DEFAULT` 的列 | 中 | 备份 + 先在别的项目试 |
| 改列名 / 改类型 | **高**（存储过程和前端都引用旧名） | 完整备份 + 恢复演练 + 同步改代码 |
| 加 CHECK / 外键 | 中（老数据可能不满足新约束而失败） | 先 `SELECT` 检查有没有违规数据 |
| 改 RLS 策略 | **极高**（可能瞬间放开或锁死数据） | 完整备份 + 改后立刻用两个账号实测 |
| `DROP TABLE` / `TRUNCATE` | **毁灭性** | 不该发生 |

## 5. 恢复操作

### 5.1 恢复单个数字（最常见）

成员误报损了 500g，正确做法**不是**去改数据库，而是**再做一笔反向操作留下记录**：

```sql
-- 1. 先查这笔操作，确认是哪一条、谁做的
SELECT id, target_name, operation_type, change_amount, previous_balance, new_balance,
       operator_name, to_char(created_at,'YYYY-MM-DD HH24:MI') AS 时间
FROM public.inventory_logs
WHERE target_name LIKE '%哑光白%'
ORDER BY created_at DESC LIMIT 10;

-- 2. 用入库操作把重量补回去（会生成新的流水，审计链完整）
```

然后让管理员在网站里对该耗材做一次「入库 500 g」，备注写清「冲销 2026-10-12 误报损」。**这是唯一既修正数据又保留真相的做法。**

### 5.2 恢复被误删的一行

```sql
-- 从你的备份 CSV 里找到那一行，手工 INSERT 回去
INSERT INTO public.reusable_tools (id, name, category_id, model_spec, total_quantity,
  available_quantity, borrowed_quantity, location_id, is_active, notes)
VALUES ('55555555-5555-5555-5555-555555550005', '罗宾汉防静电精密斜口钳 5寸',
  '22222222-2222-2222-2222-222222220004', '碳钢刃口 剪切铜丝专用', 8, 8, 0,
  '11111111-1111-1111-1111-111111110003', true, '仅限剪铜丝及打印支撑，禁止剪铁丝')
ON CONFLICT (id) DO NOTHING;
```

`ON CONFLICT DO NOTHING` 保证重复执行不会报错或插重复行。

### 5.3 灾难级恢复（整库没了）

1. **先停止一切写入**，通知成员今天不要用。
2. 确认是数据真没了，还是项目被暂停（后者只需 Restore，见后台指南第 10 节）。
3. 有档位 C 备份：新建 Supabase 项目 → 按顺序执行 01→02→03→04 迁移 → 执行备份 SQL → 验证。
4. 只有档位 B（CSV）：新项目跑迁移 → Table Editor 逐表 **Import data from CSV** → 成员重新注册。
5. 什么都没有：**只能靠 `inventory_logs` 之外没有任何东西**——实际上业务表数据会全部丢失。这就是本文存在的理由。

## 6. 密钥与凭据保护

### 6.1 四类凭据，待遇完全不同

| 凭据 | 长什么样 | 能否公开 | 泄露后果 | 泄露后怎么办 |
| :--- | :--- | :--- | :--- | :--- |
| Publishable / anon key | `sb_publishable_...` 或 `eyJhbGci...` | **能**，已提交在仓库 | 无实质后果（RLS 仍在） | 无需处理 |
| **Secret / service_role key** | `sb_secret_...` | **绝不能** | **任何人可绕过 RLS 读写全部数据** | API Keys 页立即轮换；通知成员 |
| 数据库直连密码 | 你自己设的 | 绝不能 | 可直连改库、绕过接口 | Settings → Database 重置 |
| 账号级访问令牌（PAT） | `sbp_...` | 绝不能 | **能管理你名下所有 Supabase 项目**，包括删库 | Account Settings → Tokens 立即撤销 |

### 6.2 三条习惯

1. **不要把凭据贴进聊天、群、文档、截图**。需要别人帮忙时，描述现象而不是给钥匙。
2. 临时令牌用完就撤。我这边执行迁移用的那枚 `sbp_` 令牌，**现在就该去撤销**（Account Settings → Tokens → Revoke）。
3. GitHub 仓库是公开的。提交前扫一遍：

```powershell
cd D:\Users\28322\Desktop\Qoder_Project\RestWeb_Develop\yiya_lab_inventory
git grep -n -I -e "sb_secret_" -e "sbp_" -e "service_role" -e "eyJhbGciOiJIUzI1NiJ9" -- . ":!docs"
```

预期：**没有输出**（或只有文档里的说明文字）。有输出且是真密钥，立刻撤销/轮换，并把那次提交从历史里清掉（需要维护者处理）。

### 6.3 当前密钥状态（已核查）

- 仓库内**没有** service_role、没有数据库密码、没有 PAT。
- `config.defaults.js` 只有 Project URL 与 publishable key，符合设计。
- 我在运维过程中调用过一次会返回完整密钥的接口，输出被截断，主体是可公开的 anon 钥匙；为避免任何残余风险，建议你在方便时**轮换 secret key**（轮换不影响网站，因为网站根本不用它）。

## 7. 高风险操作检查表（打印贴在实验室）

任何下面这类操作之前，逐条打勾：

- [ ] 我要做的事是「改数据」还是「改代码」？改代码走部署文档，不在这张表里。
- [ ] 已做备份，且备份文件确实在电脑上（不是「点了下载但没找到」）。
- [ ] 备份文件里有真实数据行（打开看过）。
- [ ] 我要执行的语句带了 `WHERE` 条件（`UPDATE`/`DELETE` 不带条件 = 全表）。
- [ ] 我先用同样条件跑了 `SELECT`，确认命中的行数符合预期。
- [ ] 我清楚怎么撤销它（能说出恢复步骤）。说不出 → 不要做。
- [ ] 不在成员正在使用的时间段操作（下课、晚上）。
- [ ] 涉及 RLS / 策略 / 删账号 / 结构变更 → 先让第二个人看一遍语句。

**任何时候都可以安全执行的**：所有 `SELECT`、`Table Editor` 的浏览、`Logs` 查看、`Usage` 查看、`Policies` 查看、本地改代码但不 push。

**看到这些字样立刻停手并求助**：`DROP`、`TRUNCATE`、`DELETE FROM`（无 WHERE）、`ALTER TABLE ... DROP`、`DISABLE ROW LEVEL SECURITY`、`GRANT ALL`、`reset --hard`、以及任何让你「运行这段就能修复」的不明来源脚本。
