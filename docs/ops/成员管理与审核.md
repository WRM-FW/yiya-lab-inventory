# 成员管理与审核

> 本文所有表名、列名、菜单名称均来自 2026-10-12 对项目代码与线上 Supabase 的实际检查。
> **前置提醒**：原缺陷 [R1](./运维手册总览.md) 已于 2026-10-12 修复，「管理员专区」的姓名与学号列现在能正常显示（前端已统一做 `full_name` ↔ `fullName` 映射）。若仍显示空白，先 Ctrl + F5 清掉浏览器里的旧脚本，再用本文 1.3 节的 SQL 核对数据本身。

## 1. 先搞清三套「状态」，否则一定管错

一个成员在这套系统里有三个地方描述他，**互相独立**，看到的「状态」不一致是正常现象，不是 bug：

| 位置 | 存什么 | 你在这能做什么 | 在哪看 |
| :--- | :--- | :--- | :--- |
| **Supabase Auth**（认证中心） | 邮箱、密码、账号是否被锁定、登录会话 | 建账号、删账号、发重置密码邮件、封禁 | 左侧 **Authentication → Users** |
| **`public.users_profile` 表**（业务档案） | 姓名、学号、`role`（管理员/成员）、`status`（审核状态） | 批准、驳回、禁用、提升为管理员 | 网站管理员专区，或 **Table Editor** 选 `users_profile` |
| **RLS 策略**（数据库规则） | 「什么人能读/写哪些行」 | 日常不需要改 | 左侧 **Database → Policies** |

### 1.1 真正决定数据访问权的是第三个

`users_profile.status` 只是**一张表里的一个字段**。成员能不能看到物资，取决于 RLS 策略里对 `fn_is_approved_member()` 的判断，而这个函数会实时去 `users_profile` 查 `status = 'approved'`。这条链路我实测过：

- 状态 `pending` 的成员请求物资列表 → 返回 0 行（不是报错，是空）。
- 管理员把他批准为 `approved` → 该成员**不用重新登录**，刷新页面就能看到数据。
- 管理员把他改成 `disabled` → 刷新后立刻又变成 0 行。

**所以：把状态改成 `disabled` 就是立刻生效的断权操作，不需要删账号。**

### 1.2 前端页面显示的「已登录」不可信，也不危险

网站把登录状态缓存在浏览器里，所以被禁用的成员界面上可能还显示着自己的名字、还能点进各个页面。**但每一次数据请求都会被数据库拒绝**，看不到也改不了任何数据。看到「他还能打开页面」不用惊慌，先按 1.1 确认状态字段。

### 1.3 一条 SQL 看全所有成员的真实状态

在左侧 **SQL Editor** → **New query** 粘贴后点 **Run**（这一步只读，不会改任何东西）：

```sql
SELECT
    p.email                       AS 邮箱,
    p.full_name                   AS 姓名,
    p.student_or_staff_id         AS 学号工号,
    p.role                        AS 角色,
    p.status                      AS 审核状态,
    to_char(p.created_at, 'YYYY-MM-DD HH24:MI') AS 注册时间,
    to_char(p.reviewed_at, 'YYYY-MM-DD HH24:MI') AS 审核时间,
    (a.email_confirmed_at IS NOT NULL) AS 邮箱已确认,
    (a.banned_until IS NOT NULL)       AS 认证中心已封禁
FROM public.users_profile p
LEFT JOIN auth.users a ON a.id = p.id
ORDER BY p.created_at DESC;
```

`LEFT JOIN auth.users` 是关键：它能同时告诉你「认证中心有没有这个账号」。如果 `邮箱已确认` 为 false 而 `审核状态` 是 approved，说明问题在认证侧。

## 3. 审核操作

### 3.1 批准新成员（普通成员）

1. 管理员专区 → 待审核列表 → 该行点 **✅ 准入为普通成员**。
2. 预期结果：右上角弹出绿色提示「审核决策已提交并即刻生效！」，该行从待审核卡片消失，出现在下方「在籍成员」表里，状态列显示 **正常激活**。
3. 验证：让该成员在「等待审核」页点 **刷新状态** 按钮，会回服务器重查一次，通过后自动进入控制台，**不需要重新登录**。若点了仍提示待审核，用 1.3 的 SQL 确认 `status = approved`；状态确实已批准而界面不变，就带上浏览器控制台报错找维护者。

### 3.2 提升为管理员

- 待审核成员：点 **🛡️ 设为管理员**（同时完成批准 + 提权）。
- 已在籍成员：在「在籍成员」表点 **设为管理员**（按钮会弹一次确认框）。

管理员能做什么：查看全部账号（含待审核与已禁用）、审核他人、维护存放位置与分类字典、删除物资档案（普通成员只能软停用）、恢复被禁用的账号。

**⚠️ 提权前确认这个人可靠**：管理员可以禁用其他管理员。系统有一条保护——**唯一在任管理员不能把自己降级或停用**（会返回 `ERR_LAST_ADMIN`），但两个管理员之间可以互相禁用。建议至少设两名管理员，避免单人毕业离校导致无人能审核。

### 3.3 驳回申请

1. 待审核列表 → **❌ 驳回申请**。
2. 结果：该成员状态变 `rejected`。他再次登录时会被网站直接踢回登录页（路由守卫会登出），且数据请求全部为空。
3. **注意**：驳回**不会删除认证中心的账号**，他仍然知道「这个邮箱注册过」。彻底清理见 3.6。

### 3.4 禁用离职成员

1. 在籍成员表 → 该行点 **禁用账号** → 确认。
2. 结果：状态 `已禁用`，刷新后他看不到任何数据。
3. 恢复：同一行点 **恢复激活**。

### 3.5 处理「一直待审核」的积压

```sql
SELECT email, full_name, to_char(created_at, 'YYYY-MM-DD') AS 申请日期
FROM public.users_profile
WHERE status = 'pending'
ORDER BY created_at;
```

超过两周没人处理的申请建议主动联系申请人确认是否还需要，然后驳回，避免账号堆积。

### 3.6 彻底移除一个账号（高风险）

**先备份**（见 [备份恢复与安全.md](./备份恢复与安全.md)），然后按顺序：

1. 网站内先点 **禁用账号**，让他立刻断权（这一步可逆，风险为零）。
2. 观察几天确认无人需要他的历史数据。
3. 若要真删：左侧 **Authentication → Users** → 搜索邮箱 → 行尾 **⋯** → **Delete user**。

**⚠️ 有借还记录的人删不掉**：数据库会拒绝并报外键约束错误（`tool_loans_borrower_id_fkey`），这是故意设计，防止有人通过删号抹掉借还历史。遇到这个报错说明他名下有借还单，正确做法是保留账号并禁用，或在确认责任已交接后先处理 `tool_loans` 记录（需要 SQL 且会破坏审计链，不建议）。

同样，他经手的库存流水（`inventory_logs`）不会因为删号而消失——删除时 `operator_id` 会被置空，但流水文字（`operator_name`）仍在，可追溯。

## 4. 成员忘记密码或无法登录

### 4.1 先判断卡在哪一层

让他按顺序说明现象，对照下表：

| 现象 | 卡在哪 | 去哪处理 |
| :--- | :--- | :--- |
| 提示「邮箱或密码错误」 | 认证中心 | 4.2 重置密码 |
| 登录成功但停在「等待审核」页 | 业务档案 `status = pending` | 3.1 批准 |
| 登录后页面空白、统计为 0 | 他确实没数据权限，或浏览器还跑着修复前的旧脚本 | 用 1.3 SQL 看状态；状态正常则先 Ctrl + F5 |
| 用了一小时后点什么都报错 | 原 R2 已修复（自动续期）；仍报错多为旧脚本 | 让他 Ctrl + F5 后重试 |
| 提示账号被禁用/驳回 | `status` 被改过 | 3.4 恢复激活 |
| 注册时提示邮箱已存在 | 认证中心已有该邮箱 | 4.2 或 3.6 |

### 4.2 管理员代重置密码（当前最可靠的方式）

**背景事实（已验证）**：网站没有「忘记密码」入口；`site_url` 还是 `http://localhost:3000`，即使发出重置邮件，链接也指向打不开的地址；内置发信服务限速 **每小时 2 封**。所以在你改好 Site URL 之前，走下面这条路。

方式一，**重置邮件**（需要 Site URL 已改对，否则成员收不到可用链接）：
1. 左侧 **Authentication → Users** → 找到该邮箱 → 行尾 **⋯**。
2. 点 **Send reset password**（若菜单里没有此项，说明界面已改版，用顶栏 **Search... Ctrl K** 搜 reset）。
3. 告诉成员去邮箱（含垃圾箱）点链接。

方式二，**直接改密码**（不依赖邮件，推荐用于实验室内部）：
1. **Authentication → Users** → 行尾 **⋯** → **Delete user**（先禁用他，再删）。
2. 点页面右上 **Add user**，填邮箱和一个临时密码。
3. 把临时密码当面或私聊给成员，让他登录后自行改密（站内暂无改密入口，需通过控制台或让他重新注册同名邮箱——**这是当前流程的一个缺口，见 R3**）。

**⚠️ 方式二会丢历史关联吗**：不会丢流水（`operator_name` 是文本快照），但 `operator_id` 会变，重建账号后他名下的**待归还借还单**会因为删号而受限（外键阻止删除）。所以有借还记录的人**不要用方式二**，只能走重置邮件。

### 4.3 邮箱未确认导致无法登录

本项目 `mailer_autoconfirm = true`（已验证），注册即视为已确认，实测注册后立刻用密码登录成功。若将来有人把这项关掉，会出现「注册成功但登录报 Email not confirmed」。处理：在 **Authentication → Users** 里选中该用户 → **⋯** → **Send confirmation email**，或由管理员在 **Sign In / Providers → Email** 重新打开 autoconfirm。

## 5. 误操作恢复

| 误操作 | 恢复方法 | 是否可逆 |
| :--- | :--- | :--- |
| 错把成员驳回 | 该成员不在待审核列表了。用 SQL 改回：`UPDATE public.users_profile SET status='pending' WHERE email='...';` 然后在网站正常批准 | ✅ |
| 错禁用了成员 | 在籍成员表点 **恢复激活** | ✅ |
| 错把成员提成管理员 | 同一行点 **降为成员** | ✅ |
| 错把唯一管理员降级 | 系统会拦（`ERR_LAST_ADMIN`），不会发生 | — |
| 删了认证账号 | **不可逆**，需重新建账号；历史流水的 `operator_id` 已置空 | ❌ |
| 错删了物资档案 | 普通成员只能软停用（点「停用」），管理员才可能真删。真删前无提示确认，需从备份恢复 | ❌ |

**改状态前先看清邮箱**：`UPDATE` 语句不带 `WHERE` 会改掉全表。养成先跑同样条件的 `SELECT` 确认行数的习惯：

```sql
-- 先看会改到谁
SELECT id, email, status FROM public.users_profile WHERE email = 'zhang@xxx.edu.cn';
-- 确认无误再改
UPDATE public.users_profile SET status = 'approved', role = 'member', updated_at = now()
 WHERE email = 'zhang@xxx.edu.cn';
```

## 6. 成员能否绕过网页直接改数据（你应当知道的验证方法）

结论：**不能。** 这是我在上线验收时逐条实测过的，你也可以自己复现。

| 攻击方式 | 实测结果 |
| :--- | :--- |
| 只有公开密钥、未登录时读物资表 | HTTP 401，`permission denied for table materials_3d` |
| 待审核账号读物资表 | 返回 0 行 |
| 待审核账号调用库存变更函数 | 拒绝：`ERR_NOT_APPROVED` |
| 普通成员调用审核函数把自己提成管理员 | 拒绝（身份取自登录凭证，不采信网页传来的 id） |
| 普通成员直接 PATCH 自己的档案改 `role=admin` | HTTP 403，库里角色不变 |
| 网页传来的 `p_operator_id` 伪造成别人的 UUID | 落库的流水仍是登录者本人 id 与姓名 |
| 未登录调用借出函数 | `permission denied for function fn_borrow_tool` |

想自己验证第一条，在 PowerShell 里执行（把 `<PUB_KEY>` 换成 Project Settings → API Keys 里的 Publishable key，这是可以公开的钥匙）：

```powershell
curl.exe -i "https://qbeqynsibnsvvgwyhfyy.supabase.co/rest/v1/materials_3d?select=id&limit=1" -H "apikey: <PUB_KEY>"
```

看到 `HTTP/1.1 401` 就说明：即使有人把网站代码全下载下来，也拿不到数据。

**唯一真正的信任边界提醒**：能绕过这一切的只有 `secret key`（也叫 `service_role`），它完全不受 RLS 约束。它绝不能出现在前端代码、Git 仓库、聊天记录或浏览器里。检查方法见 [备份恢复与安全.md](./备份恢复与安全.md)。
