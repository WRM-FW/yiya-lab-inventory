# 网站更新与部署

> 目标：让你能独立改掉一个错别字、换一张图、调整一处布局，并确认它真的上线了。
> 本项目**不需要构建**（没有 npm install、没有打包），仓库里的文件就是网站本身，推送即上线。

---

## 1. 先认识三台「机器」和它们的关系

```
你的电脑上的文件夹            GitHub 仓库              GitHub Pages 网址
D:\...\yiya_lab_inventory  →  WRM-FW/yiya-lab-inventory →  wrm-fw.github.io/yiya-lab-inventory/
   （你编辑这里）              （git push 到这里）        （自动发布，约 1 分钟）
```

三个动作的术语：

- **工作区**：你正在编辑的文件夹。
- **提交（commit）**：给一批改动拍一张带说明的快照，存在本地。**这一步还没上网**。
- **推送（push）**：把快照上传到 GitHub。**只有推送后网站才会变**。

反过来说：只要没 `git push`，你在本地怎么改都不影响线上，可以放心试。

## 2. 准备工作（一次性）

打开 **PowerShell**（开始菜单搜 PowerShell，不要用「以管理员身份运行」，普通权限即可）。

```powershell
# 进入项目目录（复制粘贴整行，回车）
cd D:\Users\28322\Desktop\Qoder_Project\RestWeb_Develop\yiya_lab_inventory

# 确认这是 git 仓库、当前分支是 main
git status

# 确认线上仓库地址已配置
git remote -v
# 期望看到：origin  https://github.com/WRM-FW/yiya-lab-inventory.git

# 确认登录身份已配置（会显示你的名字和邮箱，只读操作）
git config user.name
git config user.email
```

如果 `git status` 报 `not a git repository`，说明你在错的目录，检查 `cd` 的路径。

`git config user.name` 输出为空时执行（换成你自己的）：

```powershell
git config user.name "WRM-FW"
git config user.email "你的邮箱"
```

推送时若弹出 GitHub 登录：本机已用 GitHub CLI 登录过，正常会直接成功。若提示 `fatal: could not read Username`，执行 `gh auth login` 按提示走一遍（选 GitHub.com → HTTPS → Login with a Browser）。

## 3. 改一处文字（完整示例）

假设要把页脚里的「高校工程实践与材料创新研究中心」改成别的内容。

### 步骤 1：本地改文件

用任意编辑器打开 `index.html`（右键 → 打开方式 → 记事本也行，但推荐 VS Code）。改完保存。

**改哪个文件对照表**：

| 想改什么 | 改哪个文件 |
| :--- | :--- |
| 页面标题、页脚文字、图标 | `index.html` |
| 系统名称、版本号、实验室名称 | `src/js/config.js` 顶部 `APP_CONFIG` |
| 颜色、间距、字号、按钮样式 | `src/css/style.css` |
| 导航栏文字与菜单项 | `src/js/components/navbar.js` |
| 某个页面的表格列、按钮文字 | `src/js/views/对应页面.js`（如 `materials3d.js`） |
| 提示弹窗文字 | `src/js/views/*.js` 里的中文串 |
| 文档 | `docs/**.md` |

### 步骤 2：本地预览（强烈建议）

```powershell
cd D:\Users\28322\Desktop\Qoder_Project\RestWeb_Develop\yiya_lab_inventory
python -m http.server 8000
```

浏览器打开 http://localhost:8000/?mode=sandbox （加 `?mode=sandbox` 用内置示例数据看效果，不会动真实数据）。看完在 PowerShell 按 **Ctrl + C** 停掉服务。

没有 python 时用 VS Code 的 Live Server 插件，或直接用 `node` 起一个静态服务。

### 步骤 3：查看改了什么

```powershell
git status              # 列出被改动的文件
git diff index.html     # 逐行显示改动，绿色是新增、红色是删除
```

按 **q** 退出 diff 浏览。**这一步是你最好的防呆检查**：只应看到你改的那几行。如果出现大量无关改动，多半是编辑器换了行尾格式，可以先 `git checkout index.html` 撤销重来。

### 步骤 4：提交

```powershell
git add index.html
git commit -m "文案：更新页脚实验室定位说明"
```

期望输出类似 `[main 1a2b3c4] 文案：更新页脚实验室定位说明` 并显示改了几个文件几行。

`git add` 后面**建议写具体文件名**，不要用 `git add .`（会把临时文件、备份文件一起提交上去）。

### 步骤 5：推送上线

```powershell
git push origin main
```

期望输出末尾有 `xxx..yyy  main -> main`。看到 `Writing objects: 100%` 就是传完了。

### 步骤 6：确认线上生效

1. 等 60～90 秒。
2. 打开 https://wrm-fw.github.io/yiya-lab-inventory/
3. **按 Ctrl + F5 强制刷新**（普通 F5 可能仍显示浏览器缓存的旧文件）。
4. 本地预览里对，线上也对 → 完成。

## 4. 查看部署状态与处理失败

### 4.1 看部署记录

仓库页 → **Insights** → 左侧 **Pages**（或 Settings → Pages）。会显示最近一次构建的状态：`Built successfully` / `Building` / `Errored`。

也可以用命令行（需要 GitHub CLI `gh`）：

```powershell
gh api repos/WRM-FW/yiya-lab-inventory/pages/builds --jq ".[0] | {status, error, commit: .commit[0:7]}"
```

期望 `status` 为 `"built"`，`error.message` 为 `null`。

### 4.2 Pages 配置被误改怎么恢复

正确配置是：**Source = Deploy from a branch，Branch = main，Folder = / (root)**。

命令行恢复（这条我之前实测用过）：

```powershell
gh api -X POST repos/WRM-FW/yiya-lab-inventory/pages -f "source[branch]=main" -f "source[path]=/"
```

已存在时改用 `-X PUT`。若返回 `409`/`already exists` 之类，说明配置已在，忽略即可。

### 4.3 常见「推送了但网站没变」

| 原因 | 判断方法 | 处理 |
| :--- | :--- | :--- |
| 只 commit 没 push | `git status` 显示 `Your branch is ahead of 'origin/main' by N commits` | `git push origin main` |
| 推到了别的分支 | `git branch --show-current` 不是 `main` | `git push origin 你的分支` 不会上线；改回 main 或合并 |
| 浏览器缓存 | 用无痕窗口打开线上地址即正常 | Ctrl + F5 |
| 改了没保存的文件 | `git status` 显示该文件 modified | 保存后重新 add/commit |
| 构建排队 | Insights → Pages 显示 Building | 再等 1 分钟 |
| 构建失败 | 状态 Errored | 多半是 `index.html` 语法被改坏，`git revert` 回退上一次 |

## 5. 回滚（改坏了怎么退回）

**只改坏了本地，还没推送**：

```powershell
git checkout -- index.html      # 丢弃该文件的本地改动
```

**已经推送上线了**（推荐做法：新增一次「反向提交」，历史保留，最安全）：

```powershell
git log --oneline -5            # 找到出问题那次提交的编号，如 1a2b3c4
git revert 1a2b3c4 --no-edit    # 生成一次撤销它的提交
git push origin main
```

**改坏了本地且想整目录退回线上状态**（会丢弃你所有未推送的改动，**不可恢复**）：

```powershell
git fetch origin
git reset --hard origin/main
```

⚠️ `reset --hard` 是这套文档里唯一的破坏性命令，用之前确认 `git status` 里没有你还想要的东西。

## 6. 判断问题出在哪一层

按这个顺序排查，每步都有明确的判据：

```
① 网址能打开吗？
   打不开（404/白屏）→ Pages 层：看 4.1、4.2
   能打开 → ②
② 界面样式乱、按钮点了没反应、控制台报 JS 错？
   是 → 前端层：本地预览复现，看是不是刚推送的改动引起
   否 → ③
③ 数据加载报错（红色提示、请求 401/403/500）？
   401 → 登录凭证过期（R2），重新登录
   403 → RLS 拒绝，成员状态问题，见成员管理文档
   500/P0001 → 数据库函数抛的业务错误，消息里有中文原因
   全部超时 → Supabase 项目可能被暂停，见后台指南第 10 节
   否 → ④
④ 数据能加载，但显示空白/undefined/统计为 0？
   → 已知缺陷 R1（前端字段名不匹配），不是你的操作问题
```

**一个技巧**：把「本地沙箱模式」当作对照。打开 `?mode=sandbox` 如果一切正常，说明网站代码本身没坏，问题在数据库连接或权限这一侧。

## 7. 关于 Supabase CLI（当前状态与警告）

你机器上装了 Supabase CLI（`D:\Software\SupabaseCLI\supabase.exe`，版本 2.120.0）。**当前不要用 `supabase db push`**：

- 本项目的 4 个迁移是通过 Supabase 管理接口直接执行的，没有写入 CLI 的迁移账本表 `supabase_migrations.schema_migrations`（我实测该表不存在）。
- 直接跑 `db push` 会认为所有迁移都没执行过，把 5 个脚本重放一遍。脚本本身是幂等的（重放不坏数据），但 CLI 的版本记录会与实际错乱，以后更难管。
- 另外 CLI 的 `db push` 需要项目登录 + 数据库直连（要在 Settings 里开启 IPv4 直连），比走控制台麻烦。

**推荐做法**：数据库结构变更一律用「新增一个迁移文件 + 在 SQL Editor 里按顺序执行」，见 [备份恢复与安全.md](./备份恢复与安全.md)。

CLI 现在对你有用的只有只读类命令，例如 `supabase --version`。

## 8. 团队协作建议（可选）

如果将来不止你一个人改代码：

1. 不要直接推 `main`，改为开分支 → 提 Pull Request → 在 GitHub 网页上审核 diff → 合并。合并后 Pages 自动发布。
2. 每次改动尽量小、说明写清楚「改了什么、为什么」，方便回滚定位。
3. 发布前先在本地预览 + 用 `?mode=sandbox` 看过效果。
